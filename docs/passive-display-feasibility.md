# 編集・配置を保つ可視化方式の実装規模

2026-10-16、開発版1.3.0（`f60d29c`）、GNU Emacs 31.1 (Windows)で調べた。
[U+3000の表示調査](ideographic-space-display.md) を受けて、文字の可視化による
編集・配置の変化をなくす方式を比較した。製品本体・既定値は変更していない。
比較後の判断は、末尾の [当面の結論](#当面の結論) に記録した。

## 判断に使える結論

**色や枠による強調に限定すれば小規模。記号マーカーを維持して配置まで保つ方式は、
現行実装への小さな修正では済まない。**

文字合成（composition）も試した。論理列は維持できるが、カテゴリーによる折り返し、
タブの幅、合成キャッシュの共有に反例があり、そのまま「ふるまいが完全に不変」の
根拠にはできない。元の空白を通常どおり配置してから、その領域内に記号を描く
Emacs本体の機能が、強い保証を目指す場合の有力な設計候補になる。

| 選択肢 | 製品側の変更量の目安 | 工数の目安 | 達成範囲 |
| --- | --- | --- | --- |
| 色を中心とした非置換表示を選択可能にする | Lisp 50〜150行＋検証150〜300行 | 1〜3人日 | 現行の有効化・停止・Font Lockを再利用できる。任意の記号表示は提供しない。 |
| 文字合成へ置き換える | Lisp 200〜500行＋検証300〜600行 | 3〜7人日 | 固定幅の空白で列計算を改善できるが、今回の不変性の要件を満たさない。 |
| 配置後の装飾をEmacs本体に試作する | C・Lispで数百〜1,000行程度から | Windows GUIに絞った試作で1〜3人週 | 画面上の領域を変えず、点・枠・矢印などを描く。設計・ビルドから必要。 |
| 本体側の方式を複数GUI・端末へ展開する | 数千行規模も想定 | 1〜3人月以上の別プロジェクトとして扱う | 対応バックエンド、端末での代替表示、Emacs上流への導入・配布方針に左右される。 |

上表は実装済みコードの計測ではなく、以下の調査からの概算である。
特にC側は未実装・未ビルドで、不確実性が大きい。現行の `jaspace.el` は495行。
見積もりは既存のU+3000・U+0020・タブ・改行が対象で、追加Unicode文字の製品化は含めない。
既存方式を残して新方式を選択可能にする想定であり、純増行数と差分総行数は一致しない。

## 「不変」に含めるもの

本文・変更状態・undoの保持に加えて、次を分けて考える。

- `char-width` / `string-width`、各位置の `current-column` とタブ位置。
- `fill-region`、列指定の移動や矩形編集などの編集結果。
- 通常の継続、word wrap、カテゴリー・禁則処理による画面行の境界。
- 双方向表示の順序、接続字形・結合記号。
- 文字のピクセル位置、行の高さ、マウス座標と本文位置の対応。

本文だけを変えない保証は現行方式にもある。列APIだけの補正や、論理列だけを
維持する方式では、この調査の目的には足りない。
任意のフォント、ユーザーによるface変更、他の表示置換との併用まで保証するかで
実装規模は大きく変わる。今回の有限の比較を、全ての設定への保証とは扱わない。

## faceによる非置換表示

全角空白の代替文字列をnil、半角空白とタブをtにする経路は既にある。
色による強調なら、display table・文字列のdisplay property・合成を追加する必要がない。
全角空白の背景色を明示するだけなら、利用者の設定で現在も使える。

製品として方式を選べるようにする作業は、主に次の範囲になる。

- 表示方式の選択と、置換文字列・タブ・半角空白マーカーを作らない分岐。
- 読み込み時のマーカー設定に依存しないfaceの既定値と、色の設定方法。
- マーカー文字列の有無に依存している改行のFont Lock条件の整理。
- 設定切替・停止復帰・後始末と、列計算・画面配置を比較する検証。

フォント・サイズ・太さ・幅をfaceに追加すると配置は変わり得るので、
提供する装飾を色などに限定し、その条件を保証に含める必要がある。
背景色だけでは連続した同種空白の境界が見えにくく、改行の色付けは
`$` などの位置を示す記号と同じ表現力を持たない。

GUIの内側の枠も試した。両方向を負にした
`(:box (:line-width (-1 . -1) :color "red"))` は比較範囲で配置を維持した。
単一数値の `:line-width -1` と同一視しない。
[faceの仕様](https://www.gnu.org/s/emacs/manual/html_node/elisp/Face-Attributes.html)
にあるように、隣接した枠は一続きになり、各文字を独立した四角で囲む用途には足りない。
色による強調はwhitespace-modeでも選べるため、これだけではJaSpace独自の差別化は弱い。

## 文字合成の試作

### 静的合成：空白に記号を重ねる

元の全角空白を構成要素に残し、その中央へ記号を重ねる。
例えば `a`・U+3000・`b` のバッファでは次のようにできる。

```elisp
(compose-region 2 3
                (vector #x3000 '(mid-center . mid-center) ?.))
```

U+3000を含むため合成の論理幅を2桁にでき、batch試作では全位置の論理列と
`fill-region` の結果を維持した。しかしGUIではカテゴリーによる折り返しが変わった。
`□` を重ねる場合は、フォールバックフォントなどによる寸法の変化も残った。

合成に使う文字の幅・フォント・高さを一律に元の文字と同じにはできない。
また、compositionは本文のtext propertyなので、既存の合成との所有権管理、
編集・コピー時の伝播、Font Lockによる再作成、indirect bufferとの共有も扱う必要がある。

タブや改行を同じ方法で合成すると、通常の制御文字としての表示を置き換えてしまった。
`"a\tb\nc\tZ\n"` の試作では、寸法が72×32pxから64×16pxへ変わり、
画面行の先頭は `(1 5 9)` から `(1)`、タブ直後の列は8から2になった。
この方式を既存4種類へそのまま一般化できない。

### 自動合成：glyph codeだけを変える

buffer-localな `composition-function-table` を複製し、空白1文字への規則を追加した。
合成関数は、元のglyph-stringの文字・幅・bearing・ascent・descentを保ち、
同じフォント内のドットのglyph codeだけをコピーする。概念上の中心部分は次のとおり。

```elisp
;; gstringは未合成の1文字、fontはその元のfont-objectを想定。
(let* ((marker (aref (font-get-glyphs font 0 1 ".") 0))
       (result (copy-tree gstring t)))
  (when marker
    (lglyph-set-code (lgstring-glyph result 0) (aref marker 3)))
  result)
```

実測でも全体のピクセル寸法と論理列を維持した。
ただし、マーカーの実際の描画範囲は元のメトリクスと異なり得るので、
隣接文字へのはみ出し・消去・再描画まで正しいと保証する手法ではない。
元のフォントに記号がない場合や、端末では別の処理も必要になる。

カテゴリーによる折り返しも残った。両合成方式で、ＭＳ ゴシックの同じ例が
`(1 32 64 74)` から `(1 32 61 74)` へ変わった。
調べた [xdisp.cのカテゴリー判定](https://github.com/emacs-mirror/emacs/blob/a360712c9d272d950d8d8255ef74570f7e90b7d9/src/xdisp.c)
は、通常文字以外では元バッファの先頭バイトを読む分岐を持つ。
診断用にU+3000のUTF-8先頭バイトに相当するU+00E3へカテゴリー `|` を付けると、
両方式とも元の行先頭へ戻った。この経路が原因という説明と整合する。
実在するU+00E3の扱いまで変える回避策なので製品には使えない。
Emacs本体を修正して確認した結果ではない。

タブを規則の対象にすると、改行と論理列は保ったままピクセル幅だけが
72pxから17pxへ縮んだ。改行への規則はこの試作では適用されなかった。
通常のタブ展開・改行処理を保った装飾にはならない。

さらに、同じフォント・同じU+3000を、規則を別々に持つ二つのバッファで順に表示すると、
最初の合成関数は1回、次の関数は0回呼ばれた。
[composite.c](https://github.com/emacs-mirror/emacs/blob/a360712c9d272d950d8d8255ef74570f7e90b7d9/src/composite.c)
ではフォントと元の文字列を含むheaderでキャッシュを検索し、規則の関数はキーに含めない。
bufferごとのマーカー設定や解除で、キャッシュをどう分離・更新するかも追加課題になる。

## その他の方式と本体側の作業

文字列overlayや画像への置換は、幅を元へ合わせても置換オブジェクトとして扱われる。
[双方向表示の仕様](https://www.gnu.org/software/emacs/manual/html_node/elisp/Bidirectional-Display.html)
と [前回の実測](international-spaces.md#双方向表示と字形形成) の問題が残る。
before-string / after-stringによる記号追加も配置へ入るため、ゼロ幅の装飾専用層とは扱えない。

専用フォントなら元の文字コードを保って字形を変更できるが、任意フォントの元の寸法・
face・拡大率に合わせる作業と配布が必要になる。タブと改行は通常の空白字形を
差し替えるだけでは扱えず、既存機能全体の解決策にはならない。

強い保証を目指す本体側の案は、通常どおりの字形選択・列計算・bidi・折り返し・
タブ展開を終えたあと、確定した領域内へ記号を描くものである。
今回調べた標準Lisp機能には、この要件をそのまま満たす任意記号の描画口は見つからなかった。
これは利用可能な方式の調査からの設計上の判断であり、不可能性の証明ではない。

本体側では、少なくとも次を実装・検証する必要がある。

- 対象文字・装飾・色を指定する設定と、glyphへ装飾情報を渡す仕組み。
- 通常文字、タブ用の伸長glyph、改行位置への描画と領域内のクリッピング。
- カーソル・選択範囲・スクロール・部分再描画・表示切替での描画と消去。
- Windows・X系・macOSなどの描画バックエンドと、実端末での制限・代替表示。
- 二つのwindowで同じbufferを異なるサイズ・faceで表示した場合の検証。

既定の改行マーカーも追加の幅を持つため、厳密に配置を維持する方式では見た目を
再定義する必要がある。右端に空きがない場合、元のレイアウトを広げず記号を示すには、
既存領域に収める・表示を省略するなどの仕様が必要になる。
任意長の代替文字列をそのまま維持する要件とは両立しない。

## 今回の比較範囲

一時試作を用い、製品の `jaspace-mode` は有効化していない。
display table・文字列overlayは方式比較の対照であり、現行設定同士の優劣比較ではない。

- batch：U+0020・U+3000・U+202F・U+2800・U+2002・U+2003・U+2007・U+2009の8文字。
  table・overlay・背景色・内側の枠・静的ドット合成・静的四角合成の6方式で、
  `a`・対象文字・`b\tZ` の全位置の列を比較した。
  U+3000を含む英文の `fill-region` も6方式で比較した。
- GUI：ＭＳ ゴシック・Consolas・Arial、faceの `:height 120`。
  `"ab\u3000def gh 口 "`・`"漢字\u3000かな。abc "`・`"אב 12\u202f345 גד "`・
  `"a b c d e f "` を各6回繰り返し、改行を追加した。
  通常の継続・word wrap・category wrapと本文幅3通りを組み合わせた。
  フレームは42桁、右marginを6・5・4桁とした。`nobreak-char-display` はnil。
  上記6方式に自動合成を加え、各方式108条件、計756条件を比較した。
- 画面行先頭は前進を確認しながら `vertical-motion` で取得した。
  ピクセル寸法・全位置の列に加え、フレームの文字幅・高さ間隔で
  `posn-at-x-y` をサンプリングした。全ピクセルの一致を調べたものではない。

| 方式 | 寸法が変わった条件 | 画面行先頭が変わった条件 | 座標からの本文位置が変わった条件 | 論理列が変わった条件 |
| --- | ---: | ---: | ---: | ---: |
| 背景色 | 0 | 0 | 0 | 0 |
| 内側の枠 | 0 | 0 | 0 | 0 |
| 静的ドット合成 | 0 | 15 | 25 | 0 |
| 静的四角合成 | 54 | 67 | 75 | 0 |
| glyph codeだけを変える自動合成 | 0 | 7 | 7 | 0 |

各欄は108条件中の件数。反例の確認であり、変更がなかった条件にも
あらゆる編集コマンド・字形形成・カーソル動作の保証はない。
タブ・改行・先頭バイトのカテゴリー・キャッシュ共有は別の短いGUI試験で確認した。
他OS・他Emacs版・実端末、任意フォント・禁則処理全体、負荷・大規模bufferは未検証。

## 当面の結論

任意の記号・文字列で表示できる自由さと利便性を維持し、当面は現行設計を継続する。
文字合成への移行、新たな非置換表示方式、専用フォントやEmacs本体の改修は進めない。

文字合成で `fill-region` の結果を維持できる点には価値があるが、実際の利用での
支障と比べて、表現上の制約・既存機能との混在・追加の管理処理を引き受けるほどの
総合的な利点は確認できなかった。色や枠に限定する方式は、自由な記号表示という
要件を満たさない。本体改修の維持・配布も、このパッケージの範囲では負担が大きい。

現行の列計算・折り返し・編集結果への影響は引き続き案内する。
whitespace-modeにも同条件の反例があることは、影響がないという保証にも、
個別の改善を不要とする理由にも扱わない。具体的な利用上の支障が確認された場合は、
その再現条件と対応コストから改めて判断する。

whitespace側の既存の注意書きについては [併用調査への追記](whitespace-mode.md#標準側の注意書きと過去の報告)
を参照。現時点では「whitespace-modeに対して、こちらは完全にふるまいが不変」と
宣伝できる実装上・検証上の根拠は得られていない。
